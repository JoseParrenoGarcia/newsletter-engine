A Claude skill is a reusable package of instructions, resources, and optional
code that teaches Claude how to perform a specific task reliably (well,
reliably depends really on how you define this skill, and that’s what we will
cover in this post).
Unlike a prompt, which lives in a single conversation, a skill persists across
sessions and can be selected automatically when relevant. It is not just
something Claude reads, it is something Claude can decide to use.
At a glance, a skill looks simple: a markdown file with some instructions. And
for small use cases, that is often enough. Simple right?

The mental model most people miss
Well, of course it is simple if you scratch the surface of skills. As mentioned
above, most practitioners mentally model a skill as: a markdown file,
instructions at the top, maybe some examples. Claude reads it, follows it,
done. Something like this:

--name: summarise-meeting-notes
description: Summarises raw meeting notes into a short structured
recap. Use when the user provides messy notes and wants clear
next steps.

In Claude Code, skills typically live under the .claude/skills/ directory.
Each skill gets its own folder, and the folder name becomes the skill’s identity
on disk. Inside that folder, SKILL.md is the one file that must exist.
A minimal skill might look like this:

.claude/
└── skills/
└── summarise-meeting-notes/
└── SKILL.md. # Word of caution -> this has to be named
EXACTLY SKILL.md

That alone is enough to create a working skill. But in practice, robust skills
usually grow a bit more structure around that core.

The 3 optional folders you can use in a skill.
3 optional directories sit alongside SKILL.md:
scripts/ — executable code. Shell scripts, Python files, anything the
skill can invoke directly. This is where deterministic execution lives.
references/ — heavy context loaded selectively. Design
specifications, lookup tables, large reference documents. These load on
demand, not at activation.
assets/ — supporting files: templates, schemas, example outputs.

placed in the SKILL.md body loads at every activation. That distinction has a
real token cost, and across a system of many skills it compounds.

A deep dive into the fields that you can use in the
Frontmatter fields
Inside SKILL.md itself, the top section is the frontmatter: a small YAML block
that describes the skill. The Frontmatter fields are nothing more than specs
which describe the skill.
Now, you can’t add anything you want in the specs, this section needs an
actual format or schema. As of time of writing, these are the fields you can
work with:
1. (required) name . Lowercase, hyphenated, and concise.
2. (required) description. Explains what the skill does and when it
should be used.
3. (optional) license. A licence name or reference to a bundled licence
file.
4. (optional) compatibility. Environment requirements such as
product target, system packages, or network assumptions.
5. (optional) metadata. Extra key-value information such as owner,
version, or internal tags.
6. (experimental) allowed-tools. A space-delimited list of tools the skill
may use.

Encoding failure modes at the selection layer
A skill that handles only the happy path is a skill waiting to fail.
Explicit exclusions in the description (“Do NOT trigger when...”) prevent the
skill from being invoked in contexts where it will produce bad output. The
failure mode is encoded at the selection layer, before any instructions run.
This is categorically different from handling failure modes in the body — by
the time the body runs, the wrong skill has already been selected.
If you read again the screenshot of Anthropicc’s skill description, it clearly
states: “Do NOT trigger when the primary deliverable is a Word document …”
This line should prevent the wrong skill from being selected in the first place.
Takeaway: if Anthropic use it, so should you.

Structuring outputs for downstream use
A skill that ends in free-form prose may still be useful to a human reader. But
it is much harder to compose into a larger workflow than a skill that returns
something structured and predictable.

Scripts that mix reasoning and determinism.

Gmail - [TEST r0t - Paid] What the docs don't tell you about Claude Code skills

One of the most useful things a skill can do is split work between Claude’s
judgement and plain executable code.
This is what the scripts/ directory is for. In both Claude Code and the
broader Agent Skills model, skills can include executable scripts alongside
instructions and reference files. That means the skill does not have to rely on
generated text for everything. It can ask Claude to reason about what needs
doing, then hand a precise subtask to Python, Bash, or another script when
the job is better handled deterministically.
That division of labour is more important than it sounds. Claude is useful for
interpretation, prioritisation, classification, and decision-making. Scripts are
better for repeatable mechanics: validating a schema, checking section
structure, normalising a file, extracting fields, or enforcing a formatting rule. In
other words, let Claude decide, let code verify. That is usually a stronger
design than asking the model to improvise both

direction: skills should be concise, focused, and structured so Claude can
discover and use them successfully. Claude Code also places skills alongside

A skill is a workflow layer. It teaches Claude what to do, in what order, and
to what standard. But a real system usually needs more than that. It may also
need access to external data, or a separate execution context for specialised
work. That is where MCP and subagents enter the picture.
The cleanest way to think about the 3 is this:
MCP provides access
skills provide workflow logic
subagents provide execution context
The skills explained blog post from Anthropic includes a comparison table
across five primitives: Skills, Prompts, Projects, Subagents, and MCP. The
table covers persistence, what each contains, when it loads, and best-for
scenarios. The two integrations that matter most in practice are skills + MCP
and skills + subagents.

The December 2025 post on extending Claude’s capabilities uses an analogy
I find precise: MCP servers are aisles of inventory, skills are employee
expertise. MCP gives Claude access to data and tools. Skills give Claude a
defined process for using them.
Neither alone is sufficient for real agentic workflows. A skill without MCP has
to work with whatever is already in context. MCP without a skill gives Claude
data access and no structured process for acting on it. Together, they close
the loop: access the right data, apply the right process.
For example, an MCP server might expose a Notion workspace and
document how to search it correctly. A skill would then define the actual
workflow: check the project page first, then previous meeting notes, then
stakeholder context, and finally return the summary in a fixed structure.

Skills + subagents
The relationship with subagents is different.
Skills define what to do and in what sequence.
Subagents provide execution capacity and domain focus.
This difference is important because these two primitives are sometimes
conflated. Skills define the how, agents define who is doing the work (and do
it).

Once you combine these layers, skills stop being isolated utilities and start
looking like building blocks in a larger pipeline.
One step might use a skill to define a workflow.
Another might use MCP to fetch live data.
Another might run inside a subagent so the work happens in an isolated
context.
And the final output might feed into another skill or a human review
stage.
That is what makes the broader architecture feel agentic.
This is also why trying to force everything into a single skill usually goes
wrong. As soon as a workflow needs both external access and controlled
execution, the better design is usually not “make the skill smarter”. It is “give
the skill the right neighbours”.

When skills are the wrong tool.
Everything we have covered should already provide us with a view of where
skills are more useful (and hence, when they are not). Still, here are 4 bullets
that I mentally keep so that I don’t go off building skills like a mad man.
One-off tasks. If you are only going to do something once, a prompt is
usually enough. Skills carry authoring overhead. You need to name
them, describe them, structure them, test them, and maintain them. That
investment only pays off when the workflow repeats often enough for

External data access without MCP. Skills that reach directly into
external APIs or databases are fragile — difficult to test, difficult to
maintain, and blurring a boundary that exists for a reason. Data access
is MCP’s job. What to do with the data is the skill’s job. Conflating them
produces skills that are hard to debug when the data source changes.
The “one skill to rule them all” anti-pattern. A monolithic skill that
handles research, drafting, SEO optimisation, and promotion in one file
is not comprehensive — it is un-testable, un-discoverable, and unmaintainable. When a skill tries to handle multiple unrelated workflows, it
selects inconsistently and fails silently in the cases it was not designed
for.

Narrow and discoverable. A skill that does one thing reliably is more
useful than one that handles many things inconsistently. Narrow scope
makes skills easier to select, easier to test, and easier to reason about
when they fail.
Descriptions written for selection. Write in third person. Include both
what the skill does and when to use it. Use specific keywords that reflect
how users will naturally describe the task. Treat the 1,024-character limit
as design space — not a ceiling to stay comfortably below, but a budget
to deploy thoughtfully. The description is the only part of the skill Claude
reads before deciding whether to activate it.
Separate instructions from heavy context. SKILL.md carries
instructions. references/ carries context. Anything that is reference
material rather than workflow logic — style guides, specification
documents, lookup tables — belongs in references/. Keeping
SKILL.md lean preserves the three-layer loading model’s efficiency.
Test like code. The agentskills.io evaluation framework treats skills as
software artefacts: design test cases (prompt + expected output + any
input files), run with-skill and without-skill comparisons, write assertions
about the output, grade and iterate. This is a complicated topic on its
own that grants some future posts. For the moment, its enough to know
it is important to consider too.

Closing thoughts
Writing a prompt is a conversational act. Building a skill is a design act.
