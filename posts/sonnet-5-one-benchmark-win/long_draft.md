# Sonnet 5's cost story only holds up at matched effort tiers

*Both the launch chart and the backlash skip the same variable — here's what's left once you control for it.*

Anthropic's Sonnet 5 launch chart and the online backlash that followed it are both measuring Sonnet 5's cost the wrong way. The chart shows a model that improved almost everywhere. The backlash — a viral cost complaint, a wave of "this feels worse" posts — shows a model that got expensive and started acting strange. Neither picture survives contact with the actual evidence once you control for one variable both sides skip: effort level.

Sonnet 5 ships with five effort settings, and a five-point cost curve isn't a single model — it's five different economic products wearing the same name. Compare Sonnet 5 at max effort to Sonnet 4.6 at whatever effort you happened to be running, and you'll get a number. It just won't mean what you think it means. Compare Sonnet 4.6 medium to Sonnet 5 medium — the same tier, the same intended workload — and a different, much narrower story shows up: Sonnet 5 gets the same accuracy for meaningfully less money. That's a real result. It's also the only comparison in this entire launch cycle that both Anthropic's marketing and the internet's complaints managed to avoid making cleanly.

This post works through what Sonnet 5 actually changed under the hood, what Anthropic's launch chart claims, the one cost comparison that holds up, and where the rest of the discourse — hype and backlash alike — quietly swapped effort levels or model tiers mid-argument.

## What is Claude Sonnet 5's agentic upgrade?

Sonnet 5's agentic upgrade comes down to three mechanical changes: a five-level effort dial, a new tokenizer, and a swapped agent scaffold. Start with effort levels, because nothing else in this post makes sense without them. Sonnet 5 supports five: low, medium, high, xhigh, and max, with high as the default in both the API and Claude Code. Think of effort as a dial for how long the model is allowed to think and act before it has to commit to an answer — more effort means more reasoning tokens, more tool calls, more self-checking passes, and a slower, more expensive response. Low effort is a model trying to get it right on the first attempt. Max effort is a model given permission to inspect, act, test, and revise as many times as it judges useful.

That dial existed in some form before Sonnet 5. But Anthropic's own documentation contains a warning that changes how every benchmark comparison in this post has to be read: effort labels are not directly comparable across generations. Sonnet 5 medium can resemble Sonnet 4.6 high in observed thinking length. Sonnet 5 high can resemble Sonnet 4.6's previous maximum. In other words, the dial got relabeled between generations, and the same word on the box no longer buys the same amount of thinking. A benchmark run comparing "Sonnet 4.6 medium" against "Sonnet 5 medium" by name alone might actually be comparing two very different compute budgets, unless someone checks the actual token and turn counts rather than trusting the label.

The second mechanical change is the tokenizer, and it's easy to miss because Anthropic kept per-token pricing identical between generations. Sonnet 5 uses a new tokenizer that maps the same text to more tokens than before — Anthropic's own estimate is a range of roughly 1.0 to 1.35 times, with about 30% as a useful planning figure. [Simon Willison ran his own token-counter tests](https://simonwillison.net/2026/Jun/30/claude-sonnet-5/) and got sharper numbers: about 1.4x more tokens for English text, 1.33x for Spanish, 1.28x for Python code, and almost no change for Simplified Mandarin. That's not a rounding error. A request that used to cost 100,000 tokens under the old tokenizer now costs 140,000 tokens for the exact same English prompt. The price per token hasn't moved, so that request just got roughly 40% more expensive without anyone changing a price. Same tariff, different bill — a distinction that matters a great deal once cost comparisons enter the picture.

The tokenizer change also eats into the advertised context window. Sonnet 5's nominal context is still 1 million tokens, same as Sonnet 4.6 — no ambiguity there. But if identical source text now consumes roughly 1.3x as many tokens, then a document that used to fill 769,000 old-token-equivalents of that same 1-million-token window now fills the whole thing. The window is the same size on paper. The amount of your actual document that fits inside it went down. Willison also flagged that manual sampling controls — temperature, top_p, top_k — are gone; passing them now returns an error rather than being silently ignored. Adaptive thinking is on by default, and there's no more manual thinking-token budget to set by hand. Migrating to Sonnet 5 isn't a model-string swap. It's a retest of token limits, latency, and prompting assumptions that used to be safe defaults.

The last mechanical change is less about the model itself and more about the scaffolding around it, and it's the clearest illustration of why a benchmark score belongs to a system, not a model. Anthropic's Terminal-Bench 2.1 result for Sonnet 5 uses a different agent harness than earlier evaluations — mini-SWE-agent, not Terminus-2 — because Terminus-2 produced 2.7 times more timeouts at xhigh effort. Swap the harness holding the model's hand, and the completion rate changes. That's true even when the underlying model is identical. It means "Sonnet 5 scored 80.4 on Terminal-Bench" is really shorthand for "Sonnet 5, at xhigh effort, wrapped in mini-SWE-agent, with a specific timeout and memory policy, averaged 80.4 across five attempts per task." The longer sentence is the accurate one.

None of this is a criticism of Sonnet 5 as a model. It's the minimum toolkit needed to read anything that follows. A benchmark score that doesn't specify effort level, tokenizer-adjusted cost, and agent scaffold isn't incomplete out of laziness — it's missing the variables that determine whether the comparison means anything at all. Anthropic's own launch chart is the first place to apply that standard.

## What does Anthropic claim about Sonnet 5's benchmark gains?

Anthropic positions Sonnet 5 as its most agentic Sonnet, built for advanced coding, long-running agents, and professional work. The launch chart backs that framing with genuinely large numbers. On Anthropic's own system-card evaluation, Sonnet 5 rises from 58.1% to 63.2% on SWE-bench Pro — a test of fixing real, harder-than-usual GitHub issues across multiple files. It rises from 67.0% to 80.4% on Terminal-Bench 2.1, a command-line execution benchmark. FrontierCode, which grades real pull-request implementation against held-out tests, jumps from 15.1% to 38.8% — more than double. AutomationBench, an enterprise workflow-automation test, goes from 5.3% to 13.5%, also more than double in relative terms even though the absolute numbers stay low.

Those four are worth sitting with because they share a shape: agentic tasks that reward a model for persisting, checking its own work, and reaching a working end state rather than answering correctly on the first pass. That's consistent with everything the mechanics section just established — more effort, more turns, more self-verification. The gains aren't spread evenly, either. OSWorld-Verified, a computer-use benchmark, moves only 2.7 points. One CAD reasoning test without tool access is flat, essentially unchanged. Writing and long-form editing don't get a dedicated benchmark in the launch materials at all. The pattern isn't "a little better everywhere" — it's large gains concentrated specifically in long-horizon, tool-using, self-correcting work, moderate gains in knowledge and reasoning tasks, and close-to-flat results in tasks that don't reward sustained agentic behavior.

That's an honest thing for a vendor chart to show, even filtered through the vendor's own selection of which benchmarks to headline. Anthropic didn't need to publish a flat CAD result or concede that Terminal-Bench required swapping agent scaffolds mid-evaluation. The fact that both details are recoverable from the system card is a point in favor of taking the underlying numbers seriously as a description of what changed.

What the chart can't tell you, because no launch chart tells you this, is what any of those gains cost per task, or whether the effort level that produced 80.4% on Terminal-Bench is the effort level you'd actually run in production. Those are the two questions that determine whether "most agentic Sonnet" translates into "the model you should be paying for." The first place to check is the one comparison built specifically to answer it.

## Is Sonnet 5 actually cheaper at matched intelligence tiers?

Here's the comparison that actually survives scrutiny: Sonnet 4.6 running at medium effort against Sonnet 5 running at medium effort — matched tiers, not matched labels, matched by observed accuracy on the same intelligence benchmark. At that matched tier, Sonnet 5 delivers essentially the same accuracy as Sonnet 4.6 for a meaningfully lower cost per task. That's it. That's the whole claim. It's narrow by design, and it's the reason it holds up where almost nothing else in this launch cycle does — because "narrow" is what "controlled" looks like.

I've made this same mistake myself, more than once: reading a launch chart at face value, or reacting to a viral cost complaint, without first checking whether the two things being compared were even running at the same effort level. It's an easy trap, because effort level is buried in a settings dial, not printed on the chart. Once you get in the habit of asking "at what effort level?" before "is it better or cheaper?", most of the discourse around a launch stops making sense as a single argument and starts splitting into several smaller, checkable ones.

Contrast that against the number that's been circulating as if it applies to Sonnet 5 broadly. [Artificial Analysis found](https://artificialanalysis.ai/articles/claude-sonnet-5-agentic-cost) that Sonnet 5 costs $2.29 per task on their Intelligence Index — roughly twice Sonnet 4.6's cost, and about 15% more than Claude Opus 4.8, a more expensive flagship model that's supposed to cost more. That $2.29 figure isn't wrong. It's just not describing the medium-effort, matched-tier comparison. It's describing Sonnet 5 at higher effort settings, where it used roughly 40% more output tokens and around three times as many agentic turns as Sonnet 4.6 on Artificial Analysis's knowledge-work evaluations. And crucially, that cost increase came entirely from token and turn consumption, not from a higher list price — [Artificial Analysis's own model comparison page](https://artificialanalysis.ai/models/claude-sonnet-5) confirms Sonnet 5 keeps Sonnet 4.6's per-token tariff, at least at standard pricing once the launch promotion ends.

That's the mechanism worth understanding, because it's the same mechanism from the effort-level section showing up as a dollar figure. A model that's more literal about using tools, checking its work, and pursuing a working end state will, by construction, spend more tokens and more turns doing that. At low or matched-medium effort, that extra spending is modest enough that the accuracy gain more than pays for itself. At high effort and above, the extra spending compounds — more turns, more replayed context, more tool round-trips — until the total bill outpaces the accuracy gain it bought. Anthropic's launch chart shows results mostly generated at xhigh or max effort, because that's where the biggest benchmark numbers live. Artificial Analysis's headline cost figure captures Sonnet 5 running at a similarly high setting, because that's the default a lot of real usage defaults to as well. Neither number is fabricated. They're just answering "is Sonnet 5 better?" and "is Sonnet 5 cheaper?" using two different effort levels, and then getting reported side by side as if they described the same model.

So the honest one-sentence version of the matched-tier finding is this: Sonnet 5 medium beats Sonnet 4.6 medium on cost for the same accuracy, and that's a real, checkable win worth acting on. It is not evidence that Sonnet 5 is cheap, or that pushing effort higher keeps paying off at the same rate. Whether it keeps paying off is a question about the shape of the cost curve as effort increases — and that curve is exactly what the next section maps out.

## Where do Sonnet 5 cost comparisons break down?

If the matched-tier comparison is the one number that holds up, everything else in the discourse around Sonnet 5 — the hype and the backlash alike — comes from comparisons that don't control for effort level or model tier. That's true of the launch chart's biggest numbers, and it's just as true of the loudest complaints about the model. Working through where each one breaks down is the point of this section.

### What does cost-per-successful-task look like across Sonnet 5's own effort levels?

Across Sonnet 5's own effort settings, the expected cost per successful task climbs far faster than the success rate does. Before comparing Sonnet 5 to anything else, it's worth comparing Sonnet 5 to itself across its own effort dial, because that comparison alone explains most of the confusion. The right way to do this is with a single number: cost per successful task, rather than cost per attempt. If a task costs $2 per attempt and succeeds 50% of the time, the expected cost of actually getting a working result is roughly $2 divided by 0.5 — about $4. That's not the cost of a guaranteed answer; it's an expectation under a simplifying assumption that retries are independent, which they rarely are in practice. But it's a far more honest number than "cost per attempt" alone, because cost per attempt hides exactly the tradeoff that matters: does spending more per try actually buy you enough extra reliability to be worth it?

[Cursor's own benchmark, CursorBench](https://cursor.com/blog/cursorbench), publishes exactly this — cost, success rate, and step count, all inside one production coding-agent harness. Worth flagging up front: CursorBench's live methodology page currently lists version 3.1 as the current production benchmark, with a note that Cursor "updated CursorBench to 3.1 with harder problems." The cost-per-task figures that circulate for Sonnet 5's effort ladder are sourced from private evaluation data. That data isn't independently checkable against a public 3.1 leaderboard at the time of writing — so treat the specific dollar figures below as reported, not as something you can currently reproduce yourself against Cursor's live site.

With that caveat stated plainly: across Sonnet 5's effort settings on this benchmark, the expected cost to a successful task ranges from roughly $2.73 at low effort up to roughly $10.49 at max effort. The success rate climbs the whole way — from about 47.7% at low effort to about 61.5% at max. But the cost climbs faster than the accuracy does. Going from low to max effort buys you roughly 14 percentage points of success rate while multiplying expected cost-per-success by nearly four. And at the top of that curve, Sonnet 5 Max isn't even the best deal available: both a high-effort GPT-5.6 setting and Opus 4.8 at max effort reportedly reach similar or better success rates at a lower expected cost per success than Sonnet 5 Max.

None of that makes Sonnet 5 a bad model. It makes max effort a bad default. The effort dial traces a genuine cost-quality frontier — more effort reliably buys more success — but frontiers have a point past which the next unit of quality gets disproportionately expensive, and Sonnet 5's frontier bends sharply somewhere around high effort. Anthropic's launch chart lives at the expensive end of that frontier. The backlash, as it turns out, mostly lives there too.

### Why did the online backlash get the comparison wrong too?

A cost complaint went viral shortly after launch, built around a chart allegedly showing Sonnet 5's cost per Intelligence Index task as wildly out of line with competing models — the kind of screenshot that's easy to share and hard to verify after the fact. That particular claim can't be independently checked here: it circulated on X, where the underlying post isn't retrievable through the research done for this piece, so it doesn't get repeated as fact. What can be checked is a more measured, named critique that makes a similar point without needing a screenshot.

[Zvi Mowshowitz, writing on Don't Worry About the Vase](https://thezvi.substack.com/p/claude-sonnet-5-is-not-frontier-but), argues that Sonnet 5 underperforms both Opus 4.8 and a competing model called Fable 5 on several benchmarks, concluding bluntly that "if you want me to use Sonnet over Opus for most purposes, you're going to have to offer a bigger discount than that." That's a real, credentialed, non-anecdotal position — and it's worth taking seriously rather than dismissing as backlash for its own sake. It's also, notably, a comparison across different models at whatever effort settings Mowshowitz was actually using day to day, not a matched-tier comparison of Sonnet 5 against its own predecessor. Comparing Sonnet against Opus, a more expensive flagship tier, was never going to flatter Sonnet regardless of effort level — Opus exists specifically to be the more capable, more expensive option.

What makes Mowshowitz's piece useful rather than just another data point in the pile is that it doesn't stop at the complaint. He concedes genuine niches where Sonnet 5 makes sense — speed, cost-efficiency on simpler tasks, and some prompt-injection robustness gains that Anthropic's own safety evaluation also reports. That's a fair verdict: not frontier-best, but not without a lane. Compare that to the viral cost thread, which flattens the entire model into one number pulled from one effort setting and calls it a garbage bin. Both takes are skeptical of Sonnet 5. Only one of them is checking its methodology before publishing the conclusion.

The backlash has a second front beyond cost, though, and this one is harder to verify than either of the arguments above.

### Are the behavioral complaints about Sonnet 5 verified?

A report circulated shortly after launch claiming Sonnet 5 refuses commands, argues with users, and in one case told a user to go to sleep. It's a specific, vivid claim, and it would matter a great deal if it were confirmed — but the original report was unreachable through every attempt made to verify it, and no independent source describing that pattern turned up in its place. So it doesn't get repeated as established fact here.

What does have a live, findable trace is something much smaller: a single, low-engagement Hacker News thread where a developer describes Claude's explanatory tone as condescending, citing a specific example of an over-explained section header. It's one thread, a handful of comments, and it's a claim about tone and verbosity — not refusal to follow instructions, not arguing with users, nothing close to the vivid claim above. It's useful only as confirmation that some tone-related grumbling about Sonnet 5 exists and is genuinely happening somewhere online, not as evidence that it's common, representative, or connected to the unverified report at all. Anthropic's own launch materials describe Sonnet 5 as more literal and more proactive about checking its work — a real behavioral shift that could plausibly read as over-explaining or over-cautious to some users, and one that's most visible at exactly the higher effort settings where the model does more unprompted checking and re-explaining. Neither the HN thread nor the unverified report says which effort level was in use — the same missing variable that broke the cost comparisons above, just showing up as a tone complaint instead of a dollar figure. That's a much more modest and much more defensible story than "the model argues with you and won't follow commands." It's also the only version of that story with anything behind it right now.

That's two backlash claims down, both weaker on inspection than they looked on first read — one because it compared the wrong tiers, one because it couldn't be verified at all. The final piece of the contrast-and-verify exercise asks whether "better at coding" is even one claim, or two claims wearing a shared label.

### What does the coding construction-versus-review split actually show?

"Sonnet 5 is better at coding" sounds like a single fact. It's actually shorthand for at least two different tasks that don't move together: writing code, and reviewing code someone else wrote. [CodeRabbit's practitioner review](https://www.coderabbit.ai/blog/claude-sonnet-5-review) is useful precisely because it measured both and found them pulling in opposite directions.

On construction, CodeRabbit found Sonnet 5 genuinely stronger — more persistent about testing and refining a difficult implementation without needing to be prompted repeatedly, consistent with the "more literal, more proactive" behavioral shift Anthropic describes. On review, the picture flips. Precision — how often a flagged issue is actually a real bug rather than a false alarm — improved from roughly 29% with Sonnet 4.6 to somewhere around 38-40% with Sonnet 5. But strict bug-catching recall — how many of the real bugs actually present in the code get caught at all — fell from around 63% with Sonnet 4.6 to somewhere around 50-51% with Sonnet 5. Fewer false alarms, but more missed bugs. That's not a contradiction; it's a genuine tradeoff, and which side of it you want depends entirely on what a false alarm costs you versus what a missed bug costs you.

CodeRabbit also tested whether pushing Sonnet 5 to maximum effort fixed the recall problem. It didn't. Maximum effort roughly doubled the cost of the review without meaningfully recovering the bugs that medium effort was missing — the same effort-versus-payoff pattern showing up again, this time inside a single, specific task rather than across a benchmark suite. Their recommendation, grounded in that data rather than in vibes, is medium effort for most teams doing code review.

Collapse construction and review into one "coding" score and you lose exactly the information that matters for deciding whether to adopt Sonnet 5 for either task. Keep them separate, and a clear, fair picture emerges: real gain in one, a real tradeoff in the other, neither of them settled by shouting louder about the other.

After four rounds of finding the mismatched comparison underneath the claim, here's the real question: does anything about Sonnet 5's agentic story hold up once you insist on independent, non-Anthropic evidence at a sane effort level? Some of it does.

## Where does Sonnet 5 genuinely hold up, independent of Anthropic's own harness?

Strip away Anthropic's own system card entirely and ask what non-Anthropic sources, measuring Sonnet 5 in their own harnesses at reasonable effort settings, actually confirm. Two independent sources hold up, and they point in the same direction: sustained agentic coding is real, specific, evidenced progress — not a universal upgrade, but a genuine one in its lane.

CodeRabbit's construction finding from the previous section is the first piece: independently measured, stronger persistence on difficult implementation work, holding even after the review-side tradeoff is accounted for separately. The second piece is Cursor's own production coding-agent benchmark, the same CursorBench referenced earlier for its cost curve. Setting aside the specific dollar figures that couldn't be verified against the current public 3.1 leaderboard, Cursor's methodology itself is worth taking seriously: real coding sessions, drawn from actual usage inside Cursor's product, scored by an agentic grading process rather than a static answer key. Inside that harness, Sonnet 5 performs as a strong coding-agent model at reasonable effort settings — not the top of the table at every setting, but competitive, and clearly improved over Sonnet 4.6's showing on the same kind of task.

Put those two together with the mechanics from the start of this post — the tool-use proactivity, the willingness to test and re-test its own work, the scaffold changes Anthropic made specifically because the old harness couldn't keep up with the new model's persistence — and a coherent, narrower claim survives everything thrown at it in this post: Sonnet 5 is a genuine step forward for sustained agentic coding work, specifically the kind that benefits from a model willing to keep working a problem rather than answering once and stopping. That's not "best model available" and it's not "only good for one narrow thing" either. It's a real, evidenced, bounded improvement — which is a much less exciting sentence than either the launch chart or the backlash wanted to write, and a much more accurate one.

## Should you trust a launch chart or a viral tweet?

Neither, on its own. A launch chart tells you what a vendor's benchmark suite showed at the effort level that produced the biggest number. A viral tweet tells you what one person's workload felt like at whatever effort level they happened to be running, usually without saying which one. Both are real data points. Neither is a substitute for measuring your own workload at your own effort level, because the one comparison in this entire cycle that actually held up — Sonnet 4.6 medium versus Sonnet 5 medium — only held up because someone controlled for the variable everyone else skipped.

Run the same test on your own tasks, and make it a real procedure rather than a vibe check. Pick 15-20 representative tasks from your actual workload — not a benchmark suite, your workload. Run Sonnet 4.6 at your current effort setting and Sonnet 5 at the matched tier (medium against medium is the one comparison this post can vouch for; check accuracy before assuming any other pairing is matched) across at least 3 trials per task, since a single run can't tell reliability from luck. Record cost per attempt and success rate separately, then divide one by the other to get cost per successful task — that's the number that actually matters, not the sticker price. If Sonnet 5 at the matched tier beats your current cost-per-success by a meaningful margin, that's your switch signal. If you have to jump to high effort or above to see a real accuracy gain, price that jump in cost-per-success terms before assuming it's worth it — this post's own evidence says it usually isn't.

The answer might agree with the launch chart. It might agree with the backlash. It will almost certainly disagree with both a little, because your workload isn't Anthropic's benchmark suite and it isn't a stranger's tweet either.
